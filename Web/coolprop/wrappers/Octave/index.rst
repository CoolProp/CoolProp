Some Notes on GNU Octave Packages
=================================

.. warning::
    Currently, GNU Octave is built using a very specific version of the GCC toolchain and requires any add-in packages like the CoolProp wrapper to be built with the *exact same toolchain version* for GCC compatibility.  Slight deviations from this toolchain, especially the GCC version, will render the package unusable in the target version of GNU Octave.

* A per-install "site" folder is kept on Octave's path at every launch, and it's found this way::

    octave-config -p LOCALOCTFILEDIR

* On Linux, with a distro-packaged Octave (Ubuntu's ``octave``/``octave-dev``, for instance), that folder is usually tucked under ``/usr/lib/.../octave/site/oct/...`` and owned by root, so ``sudo`` is needed to drop a file there. 
* On Windows, the *official installer's* own site folder sits under ``Program Files`` and needs an administrator shell; *MSYS2 UCRT64's* site folder, on the other hand, is normally writable without elevation, since the whole install tree there is user-owned.
* When those privileges aren't available, or a shared system folder is best left alone, Octave's own no-privileges trick comes in handy: a line is added to ``~/.octaverc`` (created once, by hand, in the user's home directory) that calls ``addpath()`` on a folder that's already owned, and ``.oct`` files are dropped there from then on. Since ``~/.octaverc`` runs automatically at every Octave startup, nothing requires repeating at the top of each Octave script/session. This method is used by the CoolProp ``cmake --install .`` command that is discussed below.
* Alternatively, the same ``addpath()`` command can be used at the script/session level by placing it directly inside a single session or script, to avoid *load-every-time* behavior:

   **Example:** the folder holding ``CoolProp.oct`` is added to the Octave path inside a single Octave session/script like this (*Leaving off the .oct extension*)::

    addpath('/home/?user_name?/Some_folder/CoolProp')

* There is example code :ref:`at the end of this page <octave_example>` that demonstrates Octave calls to CoolProp functions.  This code script is generated by the build script and placed in every build directory for package verification when building the CoolProp wrapper. 

Pre-compiled Binaries
=====================
Pre-compiled release binaries are no longer supplied in CoolProp's SourceForge repository.  There are simply too many OS, hardware, and Octave version combinations to keep current and cross-combinations are binary incompatible.

User-Compiled Binaries
======================

Common Requirements
-------------------
Compilation of the Octave wrapper requires a few :ref:`common wrapper pre-requisites <wrapper_common_prereqs>`

Additional requirements:

* SWIG (see :ref:`common wrapper pre-requisites <wrapper_common_prereqs>`)
* Octave (and development headers)

Linux
-----

On Ubuntu and friends, GNU Octave and its associated build dependencies are installed this way::

    sudo apt-get install swig octave octave-dev build-essential cmake ninja-build git

.. note::
    The development package, ``octave-dev``, used to be called ``liboctave-dev`` on older Debian/Ubuntu releases. Either way, ``apt`` builds ``octave`` and its matching dev package from the same source and pins them to each other with a hard version dependency, so there's no separate compiler toolchain to match by hand.

    The Octave version that comes from ``apt`` depends on which Ubuntu release is used. **Ubuntu 24.04 LTS** ships *Octave 8.4.0* and **26.04 LTS** ships *Octave 11.1.0*, which is much closer to the current upstream version as of this update. Either way, the dev package is version-locked to its matching ``octave`` package, so the GCC compiler version is always in sync.

OSX
---

Per https://wiki.octave.org/Octave_for_macOS, there's no installer anymore for the latest GNU Octave on macOS; Homebrew is now the maintained path to the current stable release.  This has not been tested in recent years by the CoolProp team.  Following installation, it might be desirable to add the octave binary folder onto the path.  To do so, add to the file .profile (or create it) in the user's home directory::

    export PATH="/usr/local/octave/11.3.0/bin:$PATH"

.. attention::
    Testing and updating of this OSX section is requested by an OSX Octave user.  An update PR is welcome.

Windows
-------
On Windows, the situation has improved dramatically over the last several years and two routes are supported. Either one works, depending on how GNU Octave should be run on the Windows machine.  However, as noted above, a ``CoolProp.oct`` package only loads in the exact Octave version it's built against; both must use the exact GCC compiler version.

One of the two routes below should be used exclusively:

1. **The official Octave installer's own bundled toolchain (the easier route for most people)**
   Octave is downloaded and installed as usual from  `Octave for Windows <https://wiki.octave.org/Octave_for_Microsoft_Windows>`_. A matched GCC, CMake, and Python are shipped right inside the installer's own folder, reached by opening "Bash Shell" from Octave's Start Menu entry: a shell with that toolchain already first on ``PATH``, and the bundled GCC is guaranteed to match its companion Octave version. Two build tools are *not* bundled, though, and need to be added by hand once per machine; see the note in the build steps below.

   .. note::
    The Windows Installer (11.3.0) is currently, as of this page update, built on ``MSYS2 MinGW-w64``, which is now deprecated by **MSYS2** in favor of ``MSYS2 UCRT64``.  However, since the *official installer* ships the entire toolchain with Octave, it can still be used.  It is expected that subsequent versions will be forced to switch to ``MSYS2 UCRT64``. 

2. **MSYS2 UCRT64 (for the most current Octave/GCC, or when MSYS2 is already in
   use).** For this option, GNU Octave is not installed natively on Windows, it is installed and run within an ``MSYS2 UCRT64`` emulation environment.  

   * Install MSYS2 from `msys2.org <https://www.msys2.org/>`_.  
   * Open an **MSYS2 UCRT64** shell (*not MSYS, not MINGW64*) and run ``pacman -Syu`` *until it reports nothing left to do*.  
   * Then, and only then, install Octave and the build tools as follows::

       pacman -S mingw-w64-ucrt-x86_64-octave mingw-w64-ucrt-x86_64-toolchain mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja mingw-w64-ucrt-x86_64-swig

   * ``MSYS2 UCRT64`` installs its own UCRT64-based version of GNU Octave
   * See CoolProp's :ref:`MSYS2 Setup Help <MSYS2>` for more information.

   .. tip::
    The full ``pacman -Syu`` upgrade is always run *before* Octave is installed, and
    repeated until nothing is left to do. It may ask for the shell to be closed
    and reopened partway through, and that step matters. Skipping it can leave a
    GCC package conflict behind. Octave is never installed onto a partially
    upgraded MSYS2.

.. warning:: 
    **A standalone MinGW-w64 toolchain** installed apart from either recommended route above (*e.g., an old bare* ``MinGW`` *install or a distribution like* ``TDM-GCC``) isn't recommended. Nothing guarantees its GCC version matches whichever Octave it's loaded into, and a mismatch fails at module *load* time with an unhelpful "specified procedure could not be found" error, not at build time. ``TDM-GCC`` in particular also targets the older ``msvcrt.dll`` runtime rather than the ``UCRT`` runtime used by both recommended routes above, so it's doubly unsuitable.  Additionally, Microsoft's Visual C/C++ compiler (``MSVC``) is not an option.

Build
-----

**On Linux**, once the dependencies above are in place, the builder is run this way::

    # Check out the sources from GitHub
    git clone https://github.com/CoolProp/CoolProp.git
    # ...and move into the folder just created
    cd CoolProp
    # Make a build folder and change to that folder
    # The build folder must start with "build", e.g., "buildOctave"
    mkdir -p build && cd build
    # Use CMake to generate the make file
    cmake .. -DCOOLPROP_OCTAVE_MODULE=ON
    # Build the OCT file
    cmake --build .
    # (OPTIONAL) Install, and register it with ~/.octaverc for auto-loading
    cmake --install .

``CoolProp.oct`` is optionally installed in the last step under the build's own install path prefix rather than into Octave's (often root-owned) site folder. A line pointing to that path is added to the user's ``~/.octaverc`` so that the package is automatically on every Octave startup.


.. note::
    The CMake script defaults to an optimized Release build. An unoptimized build (using the switch ``-DCMAKE_BUILD_TYPE=Debug``) still works if desired.  However, there will be a noticeable delay (~30s) on the first ``CoolProp.*`` function call while the fluid library is initialized.

**On Windows**, the same build is run from whichever shell matches the Octave installation route chosen above:

From the official installer's own **Bash Shell (Recommended)**:

.. note::
    This Bash Shell doesn't actually bundle SWIG or a CMake-compatible build driver, even though its CMake reports both ``Ninja`` and ``MinGW Makefiles`` as available generators; that list is just what CMake was compiled to support, not what's installed on this machine. Two one-time fixes, neither needing admin rights:

    * **SWIG**: download ``swigwin-<version>.zip`` from `swig.org <https://www.swig.org/download.html>`_ (a self-contained build, no installer). SWIG only generates wrapper source, so it doesn't need to match the GCC/Octave toolchain the way ``CoolProp.oct`` does. Unzip it anywhere and add that folder to ``PATH`` for this session::

        export PATH="/c/path/to/swigwin-<version>:$PATH"

    * **Build driver**: ``mingw32-make.exe`` and ``ninja.exe`` are both missing, so ``-G "MinGW Makefiles"`` and ``-G Ninja`` fail. Use ``-G "MSYS Makefiles"`` instead, which runs on this shell's own bundled ``make``.

::

    # Clone the CoolProp repository in a CoolProp directory at the current location
    git clone https://github.com/CoolProp/CoolProp.git
    # Change to the CoolProp folder just created
    cd CoolProp
    # Make a build* directory and cd into that directory
    mkdir buildOct && cd buildOct
    # Create the make system for the Octave wrapper using the MSYS generator
    cmake .. -G "MSYS Makefiles" -DCOOLPROP_OCTAVE_MODULE=ON
    # Build the CoolProp wrapper package
    cmake --build .
    # (OPTIONAL) Register the package in ~/.octaverc for auto-loading
    cmake --install .

From an **MSYS2 UCRT64** shell::

    # Clone the CoolProp repository in a CoolProp directory at the current location
    git clone https://github.com/CoolProp/CoolProp.git
    # Change to the CoolProp folder just created
    cd CoolProp
    # Make a build* directory and cd into that directory
    mkdir buildOct && cd buildOct
    # Create the make system for the Octave wrapper using the Ninja generator
    cmake .. -G Ninja -DCOOLPROP_OCTAVE_MODULE=ON
    # Build the CoolProp wrapper package
    cmake --build .
    # (OPTIONAL) Register the package in ~/.octaverc for auto-loading
    cmake --install .

``cmake --install .`` works the same way here as on Linux: no administrator shell is needed, since it installs under the build's own prefix and adds that folder to ``~/.octaverc`` automatically.  Of course, the file can be saved in any desired location and the ``~/.octaverc`` file can be updated to point to the package there.

Verifying the CoolProp Build
============================

A generated Octave example is how a build is verified. The example Octave code is written straight into the build folder as ``Example.m`` and run this way::

    octave Example.m

This file can also be loaded into the GUI editor and run by pressing F5.

The first call to any ``CoolProp.*`` function can take several seconds while CoolProp's fluid library gets initialized; that's expected, not a hang. A quicker one-line check that skips the rest of the example::

    octave --no-gui --eval "CoolProp; disp(CoolProp.get_global_param_string('version'))"

From the GUI, just issue the following commands at the prompt::

    octave:1> CoolProp;
    octave:2> CoolProp.get_global_param_string("version")

The example script's two REFPROP-dependent sections print a short notice and are skipped automatically when NIST REFPROP isn't installed on the user's machine, rather than aborting the entire script on failure to load REFPROP.
